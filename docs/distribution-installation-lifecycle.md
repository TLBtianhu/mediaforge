# 软件分发、安装与卸载设计原则

本文整理一套可用于桌面软件的分发与生命周期模型。内容覆盖源码、编译产物、便携版、安装版、运行时、模型资源、配置数据和 DSH 集成。

MediaForge 作为完整示例，因为它同时具有主程序、独立运行时、模型资源、用户配置和 DSH 集成桥。

## 1. 核心结论

分发设计不应从“把文件复制到哪里”开始，而应先区分四件事：

1. 源码是开发材料。
2. 编译产物是生产分发物的中间结果。
3. 便携版是可以独立运行的分发副本。
4. 安装版是经过安装器登记的分发形态。

解耦不等于把文件撒到不同位置。职责可以通过稳定子目录实现解耦，同时保持安装、迁移和卸载都简单。

推荐模型是：

**一个安装根目录 + 固定子目录 + 必要的系统注册信息。**

## 2. 四种层次不能混淆

### 2.1 源码

源码只描述项目。用户从源码运行时，需要自行准备编译器、依赖、构建参数和运行环境，这属于开发流程，不属于开箱即用的软件分发。

### 2.2 编译产物

编译产物用于继续制作便携包、安装包和其他发布物，不是面向用户的最终分发形态。

它必须保持纯净：

- 不写用户设置、缓存、索引、模型和任务历史。
- 不包含签名私钥、访问令牌和其他秘密。
- 可以删除、重建和复现。
- 不作为日常软件安装目录使用。

开发环境与真实用户环境必须隔离。测试写入的数据应进入开发数据目录或临时数据根，不能进入真实用户配置目录。

### 2.3 便携版

便携版是经过整理的可分发副本，携带程序、资源和必要依赖，用户不需要再执行开发环境准备。

便携版的关键不是“免安装”三个字，而是：

- 可以独立运行。
- 不依赖系统级注册。
- 不依赖其他安装形态的数据目录。
- 数据位置明确、稳定、可预测。
- 通常不需要管理员权限。

便携版可以删除目录完成移除，但目录旁的数据是否保留，应由用户决定。

### 2.4 安装版

安装版除了复制程序和资源，还会通过安装器登记：

- 安装位置。
- 开始菜单快捷方式。
- 卸载项。
- 文件关联和 URL 协议（如果需要）。
- 服务、计划任务或共享组件（如果需要）。

安装版不等于必须安装到 Program Files，也不等于必须管理员权限。用户级安装同样可以拥有完整的卸载和升级能力。

## 3. 一个安装根目录，而不是到处分散

推荐用户只选择一个安装根目录，内部由应用固定管理子目录。

示例：

```text
MediaForge/
  app/                 主程序与基础资源
  data/                配置、日志、任务历史
  models/              模型资源
  runtime-envs/        独立运行时
  integrations/        DSH 适配文件
```

这样做有几个直接收益：

- 用户不需要分别选择程序、模型、运行时和集成路径。
- 安装、迁移、备份和卸载都有明确的边界。
- 各模块仍然可以独立升级、保留和清理。
- 不会出现程序、缓存、配置和服务散落在多个目录的问题。

逻辑解耦通过子目录完成，而不是通过物理分散完成。

注意：Windows 卸载项和 DSH 的注册信息属于外部状态，仍然需要分别管理，不能仅靠删除根目录假装全部清理完成。

## 4. 路径选择与权限处理是两个维度

### 4.1 减少选择成本

用户只选择安装根目录，内部路径由应用固定管理。默认路径应当让多数用户无需思考即可完成安装。

默认用户级路径示例：

```text
%LOCALAPPDATA%\Programs\MediaForge
```

用户如果希望迁移到 D 盘，也可以选择其他可写目录，例如 `D:\Apps\MediaForge`。

### 4.2 避免不必要的管理员权限

是否需要管理员权限，取决于目标目录 ACL 和安装器要修改的系统状态，不取决于盘符。

通常需要管理员权限的情况：

- Program Files 和 Program Files (x86)。
- Windows 系统目录。
- 部分 ProgramData 共享目录。
- 其他用户的个人目录。
- 系统服务、驱动、计划任务和 HKLM 配置。

通常不需要管理员权限的情况：

- 当前用户的 Desktop、Documents、Downloads。
- 当前用户的 AppData、临时目录和开始菜单目录。
- 当前用户有写权限的其他磁盘目录。
- HKCU 用户级配置。

管理员通常可以写普通用户目录，也可以修改其他用户文件，但管理员不等于 SYSTEM 或 TrustedInstaller，仍受到 UAC、所有权、沙箱和系统保护机制影响。

因此，正确策略是：

**默认用户目录解决权限问题，单一根目录解决选择和管理问题。**

## 5. 文件关联、开始菜单搜索与目录位置无关

把 exe 放进 Program Files，不会自动获得文件关联或开始菜单搜索能力。

文件关联主要依靠安装器登记：

- 整机级 `HKLM\Software\Classes`。
- 用户级 `HKCU\Software\Classes`。
- 用户对默认打开方式的选择。

开始菜单搜索主要依赖开始菜单快捷方式和 Windows Search 索引，而不是扫描 Program Files。

命令行启动则涉及 PATH、App Paths、当前目录、Shell 查找顺序和应用执行别名。

因此，安装器必须明确处理需要的系统登记，不能认为复制到某个目录就会自动完成。

## 6. 安装时的组件与选项

安装器可以提供以下组件：

- 主程序，默认安装。
- DSH 集成桥，默认勾选；如果用户不需要，可以取消。
- 数据目录和运行时目录只创建结构，不单独作为“安装内容”展示。

数据目录刚安装时通常是空的，只有在使用过程中才逐渐产生配置、模型、日志和运行时资源，所以没有必要提供“安装配置”的独立选项。

DSH 集成桥则不同。它一开始就有启动器、注册配置和进程入口，因此天然适合作为独立组件。

如果用户没有安装 DSH，勾选 DSH 兼容也只表示保留集成能力，不应影响 MediaForge 主程序的安装和使用。

## 7. DSH 集成的边界

### 7.1 DSH 宿主由 DSH 自己管理

MediaForge 不应该假设 DSH 的安装位置、版本、目录结构或配置格式，也不应该直接修改 DSH 的 profile 文件。

MediaForge 负责：

- 提供标准集成包。
- 提供 MCP 启动方式。
- 管理自己的程序、数据、模型和运行时。

DSH 负责：

- 插件目录和 profile 配置。
- 插件启用、禁用、更新和移除。
- 自己的版本和配置兼容性。

如果需要安装或移除集成，应通过 DSH 的正式插件管理接口完成，而不是直接编辑 `cordis.patch.yml`。

### 7.2 本地加载路径

本地已有 MediaForge 时，DSH 应选择集成包目录，而不是程序根目录：

```text
MediaForge\integrations\dsh-mediaforge
```

该目录包含 bundle manifest、patch、图标、启动配置和集成资源。

典型加载流程：

1. DSH 读取 bundle。
2. DSH 通过插件管理器物化并启用它。
3. DSH 根据配置启动 MediaForge MCP 客户端。
4. MCP 完成握手，形成 `mcp__mediaforge__*` 工具。

如果用户没有 DSH，整个流程不会发生，也不影响 MediaForge 独立运行。

### 7.3 DSH 的实际下载形态

当前 DSH 的插件安装实现支持以下来源：

- registry：npm 包名和版本。
- path：本地路径。
- git：Git 仓库地址。
- tarball：压缩包地址。

它通过 pnpm 物化插件包并组合 bundle patch，不是通用的软件安装器。

因此，DSH 云分发适合适配器和插件能力，不自动等于完整 MediaForge 应用分发。云端安装与完整应用安装暂不纳入当前本地模型。

## 8. 运行时、模型和配置都是独立资产

### 8.1 主程序资源

随程序附带的基础运行文件是程序的一部分，随主程序升级或卸载。

### 8.2 独立运行时

管理型运行时具有以下特点：

- 首次使用时下载、校验并激活。
- 按资产 ID 和内容哈希管理。
- 可以跨应用版本复用。
- 不应随主程序卸载被默认删除。

MediaForge 的运行时资产示例：

```text
runtime-envs/runtime-cuda-2026.11.3
```

运行时不需要单独的 Windows 卸载项，但应有独立清理选项。

### 8.3 模型资源

模型通常体积较大，下载成本高，应该与配置、日志和任务历史分开处理。

用户可能希望清理配置但保留模型和运行时，也可能希望删除模型但保留程序。卸载界面必须允许这种选择。

### 8.4 配置、日志和任务历史

这些数据与模型和运行时不同，通常体积较小，但包含用户偏好和工作记录。

默认卸载主程序时应保留。删除前必须明确提示影响。

## 9. 卸载界面应该让用户看到选择

卸载程序不应只是一个自动删除脚本。更合理的是启动卸载 exe 后显示选项框，让用户明确选择卸载范围。

推荐选项：

- 主程序。
- 独立运行时。
- 模型资源。
- 配置、日志和任务历史。
- DSH 集成桥。
- 全选。

默认只勾选主程序，其他涉及数据删除的选项默认不勾选。

选择“全选”时，应再进行一次明确确认。

### 9.1 卸载顺序

完整卸载时，合理顺序是：

1. 通过正式接口移除 DSH 集成。
2. 清理用户选择的配置、模型和运行时。
3. 删除主程序、快捷方式和安装注册项。

DSH 启动器可能位于数据目录中，所以不能只删除数据而保留一个已经失效的 DSH 注册入口。

### 9.2 卸载不是统一系统动作

Windows 没有一个统一的“系统卸载.exe”替所有软件完成卸载。

传统 Win32 卸载项通常包含显示名称、版本、安装位置和卸载命令，系统设置或控制面板读取后执行对应程序。

`unins000.exe` 只是 Inno Setup 常见的默认卸载程序名称，不是 Windows 标准。

卸载程度由安装器和应用自己定义。直接删除目录不一定等于完整卸载，残留配置本身也不必然等于恶意或违法。

## 10. Windows 和 DSH 分别看到什么？

Windows 应用管理通常只显示 MediaForge 主程序：

- 名称。
- 版本。
- 发布者。
- 安装位置。
- 卸载命令。

配置、模型和运行时不是独立 Windows 应用，不应分别出现在卸载列表中。

DSH 集成桥应出现在 DSH 的插件管理中，由 DSH 负责启用、禁用和移除，而不是再创建一个独立的 Windows 卸载项。

## 11. 三种本地状态与异常状态

正常有三种状态：

1. 有 App，也有 integrations：DSH 直接从本地集成包加载。
2. 有 App，没有 integrations：只补装集成包，不重新安装主程序。
3. App 和 integrations 都没有：需要完整应用安装包，或者使用远程 MCP 服务。

还有一种异常状态：只有 integrations、没有 App。适配器不能独立工作，应提示先安装主程序。

安装逻辑应是：缺适配补适配，缺应用补应用，已有完整环境就直接启用。

## 12. 多版本共存与升级

同一台电脑可以存在开发构建、便携副本和正式安装版，但它们必须使用不同的程序路径和数据路径，不能共享配置、缓存和任务历史。

不建议把同一软件随意重复安装到多个位置，否则可能出现：

- 文件关联被后安装版本改写。
- PATH 指向旧版本。
- 开始菜单出现多个相似入口。
- 单实例请求被转给旧进程。
- 插件和更新入口指向不同版本。
- 数据格式和模型状态不一致。

多版本共存必须显式设计，包括独立产品标识、独立数据目录和明确的默认版本选择。

升级时应默认替换主程序，保留配置、模型和运行时。升级路径应从既有安装记录解析，不应每次都强制写回默认位置。

## 13. 发布物、签名和更新迁移

正式分发时应明确：

- 版本号和产物名称。
- 运行环境和依赖关系。
- 文件大小与 SHA-256。
- 数据兼容和升级策略。
- 签名与更新验证方式。

签名私钥必须保存在仓库之外，不能随源码、构建目录或发布包分发。

签名密钥或验证公钥发生变化时，必须说明旧客户端如何升级到新客户端，不能假设旧程序一定能验证新的签名清单。

## 14. 十条通用软件开发原则

### 原则一：源码、编译产物和分发形态分开

源码服务开发，编译产物服务构建，便携版和安装版服务用户。不要把开发目录直接当成产品交付。

### 原则二：开发产物保持纯净

不写用户状态，不携带秘密，不依赖真实用户目录，可以删除和重建。

### 原则三：便携版必须自包含且数据边界明确

便携版不只是免安装，而是能够独立运行，并且知道数据写在哪里、不依赖其他安装形态。

### 原则四：安装版是正式登记，不是简单复制文件

安装器负责安装位置、卸载项和必要的系统登记。用户级安装与整机安装都应被支持并明确权限差异。

### 原则五：权限与目录选择解耦

默认用户目录避免权限问题，单一根目录减少选择成本。需要管理员权限时，必须是因为实际操作确实需要，而不是目录名字看起来高级。

### 原则六：文件关联和搜索入口由安装器明确处理

不要假设目录会自动提供文件关联、开始菜单入口或命令行查找能力。

### 原则七：职责通过稳定子目录解耦，而不是到处分散

程序、配置、模型、运行时和集成可以独立管理，同时位于同一根目录下，避免用户永远无法彻底清理。

### 原则八：卸载必须按资产类别提供选择

主程序、配置、模型、运行时和集成桥应分别处理。默认只卸载主程序，破坏性操作必须由用户明确选择。

### 原则九：宿主插件由宿主管理

DSH 之类的宿主应负责自己的插件目录和配置格式。应用只提供适配能力，通过正式接口交互，不直接修改宿主内部文件。

### 原则十：发布、升级和卸载都是生命周期，而不是文件操作

版本、校验、签名、数据保留、升级、回滚和卸载范围必须一起设计。发布成功不等于生命周期闭环，用户能安全升级和卸载才算完成。

## 15. 验收清单

一个符合本文模型的项目，至少应验证：

- 开发构建不会写真实用户数据。
- 便携版在任意可写目录中都能独立运行。
- 用户级安装不需要管理员权限。
- 自定义安装目录时会检查可写性。
- 主程序、配置、模型、运行时和集成桥有明确边界。
- 升级不会默认删除用户数据。
- 卸载界面可以选择清理范围。
- DSH 集成通过正式插件管理接口安装和移除。
- Windows 卸载项与 DSH 插件状态都被正确处理。
- 发布物有版本、大小、哈希和更新迁移说明。

这套模型的重点不是创造更多目录和安装器，而是减少用户需要理解的路径和状态，同时保留各资产独立管理的灵活性。
