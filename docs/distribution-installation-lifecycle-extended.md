# 软件分发、安装与卸载设计原则（拓展版）

本文是 `distribution-installation-lifecycle.md` 的拓展版，面向需要同时处理主程序、便携包、安装包、运行时、模型、配置和宿主插件的项目。

MediaForge 作为完整示例，因为它同时具有编译产物、便携版、安装版、独立运行时、模型资源、配置数据和 DSH 集成桥。

## 1. 先区分四件事

### 1.1 源码

源码是开发材料，不是最终用户运行形态。用户从源码开始，需要自己准备编译器、依赖、构建参数和运行环境，这属于开发流程。

### 1.2 编译产物

编译产物的核心工作，是把高级语言转换成机器码或目标平台可执行格式。

它不应该负责：

- 注册表和文件关联。
- 数据目录和模型目录。
- 宿主插件注册。
- 运行时下载和激活。
- 卸载策略和用户数据保留。

编译产物属于开发环境，必须保持纯净，不写设置、缓存、索引、模型和任务历史，不包含签名私钥和访问令牌，不作为最终分发形态交给用户使用。

### 1.3 便携版

便携版是经过整理的可分发副本，携带程序、资源和必要依赖，能够独立运行。

它的重点是：

- 程序、资源和必要依赖已经摆好。
- 数据位置明确、稳定、可预测。
- 不依赖系统级注册。
- 不依赖其他安装形态的数据目录。
- 通常不需要管理员权限。

便携版不是“随便复制一下编译目录”，而是独立的打包结果，应有自己的打包脚本和验证流程。

### 1.4 安装版

安装版不仅复制程序，还通过安装器执行安装策略：

- 选择安装位置。
- 创建目录结构。
- 注册卸载项和开始菜单入口。
- 处理文件关联、URL 协议或共享组件（如需要）。
- 保留或清理指定数据。
- 提供升级和卸载路径。

安装版不等于必须装进 Program Files，也不等于必须管理员权限。用户级安装同样可以拥有完整的安装、升级和卸载能力。

## 2. 状态模型与动作模型

便携版偏向状态模型：把已经摆好、关联好、可独立运行的状态交给用户。

安装版偏向动作模型：声明并执行如何摆放、注册、加载、升级和卸载的策略。

动作模型通常有更丰富的定制能力，状态模型通常更容易预测和复现。两者不是谁替代谁，而是服务不同的使用方式。

Windows 的 exe 先验让编译产物和便携版看起来相似，但这只是巧合。真正的安装层还需要处理引用、环境变量、注册表、运行时和卸载链。

因此，便携版打包脚本和安装包打包脚本应该分别维护，即使前者短很多，也不应混用职责。

## 3. 一个安装根目录，而不是到处分散

推荐用户只选择一个安装根目录，内部由应用固定管理子目录。

示例：

```text
MediaForge/
  app/                 主程序与基础资源
  data/                配置、日志、任务历史
  models/              模型资源
  runtime-envs/        独立运行时
  integrations/        DSH 适配文件
```

这样做的好处：

- 用户不需要分别选择多个路径。
- 安装、迁移、备份和卸载都有明确边界。
- 各模块仍可独立升级和清理。
- 不会出现程序、缓存、配置和插件散落多个目录的问题。

解耦通过子目录完成，而不是通过物理分散完成。

但 Windows 卸载项和 DSH 的注册信息属于外部状态，仍需单独处理，不能认为删除根目录就自动完成全部清理。

## 4. 路径选择与权限处理解耦

### 减少选择成本

用户只选安装根目录，内部路径由应用固定管理。默认用户级路径可避免多数用户纠结安装位置。

### 避免不必要的管理员权限

是否需要管理员权限，取决于目标目录 ACL 和安装器要修改的系统状态，不取决于盘符。

通常需要管理员权限：

- Program Files 和 Program Files (x86)。
- Windows 系统目录。
- 部分 ProgramData 共享目录。
- 其他用户的个人目录。
- 系统服务、驱动、计划任务和 HKLM 配置。

通常不需要管理员权限：

- 当前用户的 Desktop、Documents、Downloads。
- 当前用户的 AppData、临时目录和开始菜单目录。
- 当前用户有写权限的其他磁盘目录。
- HKCU 用户级配置。

管理员通常可以写普通用户目录，也可以修改其他用户文件，但管理员不等于 SYSTEM 或 TrustedInstaller，仍受到 UAC、所有权、沙箱和系统保护机制影响。

正确策略是：

**默认用户目录解决权限问题，单一根目录解决选择和管理问题。**

## 5. 文件关联、开始菜单搜索与目录位置无关

把 exe 放进 Program Files，不会自动获得文件关联或开始菜单搜索能力。

文件关联主要依靠安装器登记：

- 整机级 `HKLM\Software\Classes`。
- 用户级 `HKCU\Software\Classes`。
- 用户对默认打开方式的选择。

开始菜单搜索主要依赖开始菜单快捷方式和 Windows Search 索引，而不是扫描 Program Files。

命令行启动则涉及 PATH、App Paths、当前目录、Shell 查找顺序和应用执行别名。

安装器必须明确处理需要的系统登记，不能认为复制到某个目录就会自动完成。

## 6. 安装包是启动和恢复特权入口

安装包不应变成只创建目录的空壳，但也不能承担所有更新工作。

合理分工是：

### 安装包负责

- 首次安装主程序。
- 创建必要目录结构。
- 注册卸载项和开始菜单入口。
- 在损坏恢复或跨大版本变化时重新部署 `app`。
- 必要时全量覆盖 `app` 子目录。

### 软件内部更新负责

- 按版本管理运行时资产。
- 按版本管理模型、配置和集成适配器。
- 处理日常小版本更新和数据兼容。

推荐原则：

**安装包负责启动与恢复，内部更新负责日常迭代。**

如果安装包连 `app` 都不覆盖，首次安装和损坏恢复就会失去入口；如果所有更新都交给安装包，又会重复下载和覆盖大资产，破坏复用性。

## 7. 子目录更新规则

不同子目录不应使用同一种更新策略。

### `app`

安装包可以全量覆盖。它是程序本体和更新引擎的入口。

### `data`

不存在则创建，存在则不盲目覆盖。配置、日志和任务历史默认保留，只有明确选择清理时才删除。

### `models`

不存在则创建，存在时由软件内部按模型版本和哈希管理，不应由安装包无差别覆盖。

### `integrations`

不存在则创建，存在时按适配器版本处理。宿主插件注册由宿主自己的插件管理器负责。

### `runtime-envs`

由软件内部按资产 ID、大小和 SHA-256 管理。安装包不应反复覆盖独立运行时，避免重复下载和破坏复用。

这套规则让安装包保持简单，同时保留内部更新的精细控制。

## 8. 1.0 之前不做旧结构迁移

“不做向下兼容”不是不更新，而是**不承诺旧结构自动迁移**。

子目录架构稳定时，可以复用模型、运行时、配置和历史，更新继续按版本推进。

如果子目录架构发生变化：

- 不假装旧结构仍然存在。
- 不做复杂迁移脚本。
- 先卸载旧结构，再按新结构重新安装。
- 由用户决定是否保留或清理旧数据目录。

这样更新逻辑更简单，也避免每次结构调整都编写一套迁移方案。

注意：这要求安装包必须提供清晰的卸载和恢复入口，不能让用户无路可退。

## 9. DSH 集成边界

### 9.1 宿主由宿主管理

MediaForge 不应假设 DSH 的安装位置、版本、目录结构或配置格式，也不应直接修改 DSH 的 profile 文件。

MediaForge 负责：

- 提供标准集成包。
- 提供 MCP 启动方式。
- 管理自己的程序、数据、模型和运行时。

DSH 负责：

- 插件目录和 profile 配置。
- 插件启用、禁用、更新和移除。
- 自己的版本和配置兼容性。

安装或移除集成时，应通过 DSH 正式插件管理接口完成，而不是直接编辑 `cordis.patch.yml`。

### 9.2 本地加载路径

本地已有 MediaForge 时，DSH 应选择集成包目录：

```text
MediaForge\integrations\dsh-mediaforge
```

而不是 MediaForge 程序根目录。

典型加载流程：

1. DSH 读取 bundle。
2. DSH 通过插件管理器物化并启用它。
3. DSH 根据配置启动 MediaForge MCP 客户端。
4. MCP 完成握手，形成 `mcp__mediaforge__*` 工具。

没有 DSH 时，集成流程不发生，也不影响 MediaForge 独立运行。

### 9.3 DSH 实际下载形态

当前 DSH 插件安装支持：

- registry：npm 包名和版本。
- path：本地路径。
- git：Git 仓库地址。
- tarball：压缩包地址。

它通过 pnpm 物化插件包并组合 bundle patch，不是通用的软件安装器。

因此，DSH 云分发适合适配器和插件能力，不自动等于完整应用分发。云端安装与完整应用安装暂不纳入当前本地模型。

## 10. 运行时、模型和配置是独立资产

### 主程序资源

随程序附带的基础运行文件是程序的一部分，随主程序升级或卸载。

### 独立运行时

管理型运行时具有以下特点：

- 首次使用时下载、校验并激活。
- 按资产 ID 和内容哈希管理。
- 可以跨应用版本复用。
- 不应随主程序卸载被默认删除。

运行时不需要单独的 Windows 卸载项，但应有独立清理选项。

### 模型资源

模型通常体积较大，下载成本高，应与配置、日志和任务历史分开处理。

用户可能希望清理配置但保留模型和运行时，也可能希望删除模型但保留程序。卸载界面必须允许这种选择。

### 配置、日志和任务历史

这些数据与模型和运行时不同，通常体积较小，但包含用户偏好和工作记录。

默认卸载主程序时应保留，删除前必须明确提示影响。

## 11. 卸载界面应该让用户看到选择

卸载程序不应只是一个自动删除脚本。更合理的是启动卸载 exe 后显示选项框，让用户明确选择卸载范围。

推荐选项：

- 主程序。
- 独立运行时。
- 模型资源。
- 配置、日志和任务历史。
- DSH 集成桥。
- 全选。

默认只勾选主程序，其他涉及数据删除的选项默认不勾选。

选择“全选”时，应再进行一次明确确认。

### 卸载顺序

完整卸载时，合理顺序是：

1. 通过正式接口移除 DSH 集成。
2. 清理用户选择的配置、模型和运行时。
3. 删除主程序、快捷方式和安装注册项。

DSH 启动器可能位于数据目录中，所以不能只删除数据而保留一个已经失效的 DSH 注册入口。

### 卸载不是统一系统动作

Windows 没有一个统一的“系统卸载.exe”替所有软件完成卸载。

传统 Win32 卸载项通常包含显示名称、版本、安装位置和卸载命令，系统设置或控制面板读取后执行对应程序。

`unins000.exe` 只是 Inno Setup 常见的默认卸载程序名称，不是 Windows 标准。

卸载程度由安装器和应用自己定义。直接删除目录不一定等于完整卸载，残留配置本身也不必然等于恶意或违法。

## 12. Windows 和 DSH 分别看到什么？

Windows 应用管理通常只显示 MediaForge 主程序：

- 名称。
- 版本。
- 发布者。
- 安装位置。
- 卸载命令。

配置、模型和运行时不是独立 Windows 应用，不应分别出现在卸载列表中。

DSH 集成桥应出现在 DSH 的插件管理中，由 DSH 负责启用、禁用和移除，而不是再创建一个独立的 Windows 卸载项。

## 13. 三种本地状态与异常状态

正常有三种状态：

1. 有 App，也有 integrations：DSH 直接从本地集成包加载。
2. 有 App，没有 integrations：只补装集成包，不重新安装主程序。
3. App 和 integrations 都没有：需要完整应用安装包，或者使用远程 MCP 服务。

还有一种异常状态：只有 integrations、没有 App。适配器不能独立工作，应提示先安装主程序。

安装逻辑应是：缺适配补适配，缺应用补应用，已有完整环境就直接启用。

## 14. 多版本共存与升级

同一台电脑可以存在开发构建、便携副本和正式安装版，但它们必须使用不同的程序路径和数据路径，不能共享配置、缓存和任务历史。

不建议把同一软件随意重复安装到多个位置，否则可能出现：

- 文件关联被后安装版本改写。
- PATH 指向旧版本。
- 开始菜单出现多个相似入口。
- 单实例请求被转给旧进程。
- 插件和更新入口指向不同版本。
- 数据格式和模型状态不一致。

多版本共存必须显式设计，包括独立产品标识、独立数据目录和明确的默认版本选择。

升级时应默认替换主程序，保留配置、模型和运行时。升级路径应从既有安装记录解析，不应每次都强制写回默认位置。

## 15. 发布物、签名和更新迁移

正式分发时应明确：

- 版本号和产物名称。
- 运行环境和依赖关系。
- 文件大小与 SHA-256。
- 数据兼容和升级策略。
- 签名与更新验证方式。

签名私钥必须保存在仓库之外，不能随源码、构建目录或发布包分发。

签名密钥或验证公钥发生变化时，必须说明旧客户端如何升级到新客户端，不能假设旧程序一定能验证新的签名清单。

## 16. 运行时重定位是必须验证的契约

这次首装失败暴露了一个重要教训：**运行时资产不能只考虑下载和解包，还必须考虑重定位。**

运行时包中的配置可能包含制作环境或旧安装目录的绝对路径。旧目录被卸载后，解释器就会失败。

因此，激活前必须：

1. 按实际资产目录重写运行时配置。
2. 验证 `home` 和 `executable` 指向真实存在的解释器。
3. 运行解释器自检，而不是只看 zip 是否解包成功。
4. 再写入 `active-runtime.json` 和资产标记。

以 Python `pyvenv.cfg` 为例，正确形式应类似：

```text
home = <runtime-root>\Scripts
include-system-site-packages = false
executable = <runtime-root>\Scripts\python.exe
```

不能保留指向旧安装目录的 `home`，也不能让 Python 去查找 `<runtime-root>\python.exe`（缺少 `Scripts`）。

`command` 这类元数据不是正常启动必需项，不应被误解为每次启动都要执行的安装命令。配置生成要避免递归启动和重复创建环境。

## 17. 打包与测试过程中的资源教训

### 不要重复制造大型运行时副本

每次首装测试都会解包完整运行时。如果不及时清理，几十 GB 的临时目录很快就会积累。

测试应：

- 优先使用小型 fixture 验证协议和生命周期。
- 只对必要的真实运行时做一次完整验证。
- 清理精确匹配的临时目录，不使用模糊删除。
- 保留真实用户数据、模型和正式发布物。

### 防止测试进程失控

递归启动的解释器可能在短时间内产生大量子进程，导致 CPU、内存和磁盘压力。

验证时应：

- 限制解释器自检的命令和参数。
- 观察进程数量，异常时立即停止。
- 只停止精确匹配测试路径的进程。
- 不使用可能影响其他应用的全局进程清理命令。

### 静默卸载与交互卸载分开

静默模式不应创建交互式卸载选项窗体，否则自动化卸载可能卡住。

应分别验证：

- 静默卸载默认只删除主程序并保留数据。
- 交互卸载时用户可以选择清理范围。

## 18. 十条通用软件开发原则

### 原则一：源码、编译产物和分发形态分开

源码服务开发，编译产物服务构建，便携版和安装版服务用户。不要把开发目录直接当成产品交付。

### 原则二：开发产物保持纯净

不写用户状态，不携带秘密，不依赖真实用户目录，可以删除和重建。

### 原则三：便携版必须自包含且数据边界明确

便携版不只是免安装，而是能够独立运行，并且知道数据写在哪里、不依赖其他安装形态。

### 原则四：安装版是正式登记，不是简单复制文件

安装器负责安装位置、卸载项和必要的系统登记。用户级安装与整机安装都应被支持并明确权限差异。

### 原则五：权限与目录选择解耦

默认用户目录避免权限问题，单一根目录减少选择成本。需要管理员权限时，必须是因为实际操作确实需要，而不是目录名字看起来高级。

### 原则六：文件关联和搜索入口由安装器明确处理

不要假设目录会自动提供文件关联、开始菜单入口或命令行查找能力。

### 原则七：职责通过稳定子目录解耦，而不是到处分散

程序、配置、模型、运行时和集成可以独立管理，同时位于同一根目录下，避免用户永远无法彻底清理。

### 原则八：卸载必须按资产类别提供选择

主程序、配置、模型、运行时和集成桥应分别处理。默认只卸载主程序，破坏性操作必须由用户明确选择。

### 原则九：宿主插件由宿主管理

DSH 之类的宿主应负责自己的插件目录和配置格式。应用只提供适配能力，通过正式接口交互，不直接修改宿主内部文件。

### 原则十：发布、升级和卸载都是生命周期，而不是文件操作

版本、校验、签名、数据保留、升级、回滚和卸载范围必须一起设计。发布成功不等于生命周期闭环，用户能安全升级和卸载才算完成。

## 19. 验收清单

一个符合本文模型的项目，至少应验证：

- 开发构建不会写真实用户数据。
- 便携版在任意可写目录中都能独立运行。
- 用户级安装不需要管理员权限。
- 自定义安装目录时会检查可写性。
- 主程序、配置、模型、运行时和集成桥有明确边界。
- 安装包能完成首次部署和损坏恢复。
- 日常更新不会默认覆盖大资产和用户数据。
- 运行时在任意目标目录都能完成配置重定位和解释器自检。
- `active-runtime.json` 只在解释器验证成功后写入。
- 卸载界面可以选择清理范围，静默卸载不会卡住。
- DSH 集成通过正式插件管理接口安装和移除。
- 测试不会留下大型运行时副本或失控的子进程。
- Windows 卸载项与 DSH 插件状态都被正确处理。
- 发布物有版本、大小、哈希和更新迁移说明。

这套模型的重点不是创造更多目录和安装器，而是减少用户需要理解的路径和状态，同时保留各资产独立管理的灵活性。
