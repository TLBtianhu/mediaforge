## 1.9 P2 增量账本（同一工作区）

**问题**（临时 fixture 实测，测完已删）：1000 个任务、每个 200 条日志时，一次完整快照要
`read_jobs` 645 ms（Python，逐文件抢写锁），IPC 载荷 37.7 MiB，而活动期每 2 秒轮询一次全量。

**已实现**：
1. **读取缓存**：Rust（`src-tauri/src/python/task_journal.rs`）与 Python（`python/core/job_store.py`）都按
   文件指纹缓存已校验记录，未变化的文件不重新解析、不抢逐文件锁；原子替换必然改变创建时间/文件索引，
   因此不会读到陈旧快照；文件消失会从缓存中剔除。
   Rust 用 `(len, modified, created)`（长度相同且落在同一时钟刻度的两次替换仅靠 `len+modified` 区分不出来）；
   Python 用 `(st_ino, st_mtime_ns, st_size, st_ctime_ns)`。
   Python 返回的是**共享只读记录**，唯一需要改写的 Kernel 恢复路径本身就是重新读盘后再写。
2. **增量信封**：`agent_jobs` / `enqueue_audio_jobs` 返回 `schemaVersion 3`：
   `{schemaVersion, full, jobs, removed, dataRoot, jobsDir}`。
   - 无 `known` → 权威全量快照（首次加载、恢复、诊断、测试）。
   - `known = {jobId: updatedAt}` → 只回 `updatedAt` 变化的记录，`removed` 列出磁盘上已消失的已知ID。
   - 非法 `known` 明确报错，不退化成空列表；旧 schema 2 信封被拒绝。
3. **前端合并**：`mediaJobs` 发送已知版本、增量合并、丢弃 `removed`（本地尚未落盘的 pending 除外），
   并在**合并后的整个集合**上重做音频组闭包校验；校验失败不发布（不会半应用）。
4. **回归用例**：Rust 覆盖缓存失效、未变化不重解析、增量只回变化/删除、240 任务长历史无丢无重；
   Python 覆盖未变化不重读、替换必重读、删除不残留、坏文件不被缓存吞掉；
   前端覆盖 `known` 上报、陈旧增量不倒退实时进度、损坏增量不半应用、已删除不被复活。

**实测（debug 构建，1000 任务 × 200 日志）**：
Rust：全量 1000 ms / 22.8 MiB；无变化轮询 **23 ms / 2 B**；单任务变化 **24 ms / 22.8 KiB**。
Python（Kernel/桥接路径）：整表读 662 ms → 稳定轮询 **15–17 ms**。
未做：跨进程变更通知、日志按需加载、修订号；`list()` 全量路径仍会克隆全部记录（只在首载/对账用）。

**契约随之调整**：catalog 读取对指纹未变的文件不再抢 write 锁，因此可能在写入者尚未发布时返回上一版
已校验记录。原子替换没有半写状态，读取不会看到中间内容；替换提交后指纹改变，下一次读取必然重读。
`docs/job-ledger-contract.md` 已同步，原“读取必须阻塞等待写入者”的断言改为
“未变化文件不阻塞 + 发布后必见新版本”。

非文字用法按语义归位——hover 填充 `--primary-hover`（新增 token，来自 palette 的 primaryHover）、

`primaryInk` 由 `readableInk(strong 种子, heading, [surface, surface1, primarySoft])` 求解；
`global.scss` 两个派生默认值曾被校验测试抓到与实际不符（`--on-primary` 写成白色，而深色粉彩填充上应为近黑），
现在默认值等于 `resolveThemeTokens('dark','blue')` 的结果，并由矩阵测试逐值断言。

验证：112 次页面加载的对比度审计 **0 处**非压暗问题（416 压暗标题 + 20 计数）；与第 1 步截图相比
0.07–0.17% 像素差异（accent 文字/图标略微变深），其余一致。

## 1.15 主题第 3 步：调色板收敛

每个 accent 的调色板从 9 个手写值缩到 4 个输入：`fill`、`ink 种子`、4 个 tint 强度、`preview`。
其余全部派生：

- `primarySoft / Softer / Border / Glow`：`rgba(fill, α)`，RGB 与 fill 不可能再漂移
  （青色此前因手改 fill 而残留旧色相 `rgb(35,140,123)`，是真实 bug）；
- `primaryHover / primaryPressed`：朝“远离标签墨色”的方向混 12% / 24%，所以粉彩填充悬停变亮、
  饱和填充悬停变暗，按钮标签墨色在三种状态下都不翻转；
- 矩阵测试新增断言：`onPrimary` 在 fill / hover / pressed 上都 ≥4.5:1；
- `global.scss` 的默认值逐值对照 `resolveThemeTokens('dark','blue')`（hex 与 rgba 都比，不只对名字）。

字面颜色因此从 360 降到 **315**；静态页面与第 2 步截图 **0.00% 像素差异**（派生值只改变悬停/按下态）。
顺带修了自己测试里的一个脆弱点：`Date.now` 桩用 `base ± 1ms` 判断窗口边界，实际会在冷启动几毫秒后翻车；
改成 ±60s 后全量套件稳定通过。

## 1.16 主题第 4 步：混合空间换成 Oklab

调研（`docs/theme-research.md`）确认了专家共识与我们的偏差：sRGB/HSL 线性插值不感知均匀，
所以"同一个权重"在不同色相上不是同一个亮度步长，往近灰锚点混还会旋转色相。

`themeMath.mixToward` 内部改为 **Oklab**（OKLCH 的 cartesian 形式），API 与全部调用点不变。
没有直接用 OKLCH：极坐标插值在近灰锚点上 hue 无意义，实测把琥珀 ink（`#e58a00` → 浅灰）
插成了粉色 `#ecafd1`；Oklab 对 a/b 线性插值只收缩彩度、保持色相。

- 新增 `tests/themeMath.test.mjs`（6 项）：端点精确、近灰锚点保色相、同权重压缩对比度离散、
  混合方向单调、越界不出 NaN、alpha 合成仍在 sRGB。
- 对比度矩阵 18 项全过；112 次页面加载审计非压暗问题 **0**。
- 与第 3 步截图相比差异 **0.13–0.19%** 像素（派生色轻微变化），其余像素一致。
- `global.scss` 的 `--primary-hover` / `--primary-pressed` 默认值同步到新派生结果，矩阵测试逐值把关。

## 1.17 主题第 5 步：wash 由感知步长求解

tone 的调色板只剩四个色相；`TONE_WASH_STEP = 0.05`（Oklab L）成为"淡底多强"的唯一输入，
α 由二分求解得出：浅色主题蓝 0.118 / 紫 0.126 / 琥珀 0.172 / 青 0.132，深色主题 0.089–0.124。

改之前实测：同样 α 下琥珀的感知步长是蓝色的 **1.7 倍**（0.0822 vs 0.0488），这正是
"手挑 α 不是可移植单位"的直接证据。改之后四种 tone 在两种主题下都落在 0.048–0.053。

- 矩阵测试新增断言：`|ΔL(wash over surface/surface1) − 0.05| < 0.012`；
- 112 次页面加载审计非压暗问题仍为 **0**；
- 与第 4 步截图相比：媒体页 8.6–9.2%、设置页 1.7%（差异全部在淡底区域）；
- `global.scss` 的四个 `--tone-wash-*` 默认值同步，测试逐值校验。

## 1.18 主题第 6 步：用 faint token 取代文字 opacity

审计最后剩下的 440 处（416 侧边栏分组标题 + 20 计数 + 4 其他）全部来自"用 `opacity` 表达层级"。
现在换成 `--on-surface-faint`：二分求解出的"在 surface / surface1 / surface2 上都 ≥4.5 的最暗颜色"。

- 深色 `#898f99`（surface 5.71:1、surface2 4.61:1），浅色 `#616d80`（4.84–5.11:1）；
- 矩阵测试断言它既过 AA、又确实比 `--on-surface-muted` 更暗；
- 替换点：`.nav-group__label`、模型页 tab 计数（含 active 态改用 `--primary-ink`）、
  工作流类型筛选与分组计数；
- **112 次页面加载的对比度审计第一次到 0**（此前 440）。

代价要说清楚：浅色主题的 faint 只比 muted 暗约 12%——AA 已是地板，想更暗只能降标准或调字重。

## 1.19 主题第 7 步：画布随主题走

LiteGraph 的调色板原来是组件里写死的六个深色值，且只在挂载时应用一次，所以切到浅色主题后画布仍是
深色——这是主题线最后一个用户可见的 bug。

- 新增 `src/litegraph/canvasTheme.ts`：`canvasThemeFor(tokens)` 把 surface / surface1 / surface2 /
  on-surface-heading / primary 映射成画布颜色；事件连线保持身份色（数据类型，不随主题）。
- 工作流编辑器：`applyTheme()` 改读 token，并新增
  `watch([themeMode, themeAccent, themeIsDark])` → `applyTheme()` + `canvas.setDirty(true, true)`。
- `.canvas-wrap` 的 `#16181d` 换成 `var(--surface)`。
- 矩阵测试 +1：画布颜色必须来自 token、节点文字在两种主题下都 ≥4.5；字面颜色总数因此从 316 降到 308
  （画布的六个硬编码色消失）。

**验证边界**：单测与构建覆盖了映射与对比度；**真实重绘只能在 WebView2 窗口里看到**，无头浏览器拿不到
LiteGraph 的渲染环境，需要开一次窗口切主题确认。

## 1.23 P2 第四刀：损坏的运行时指针不再静默换解释器

`resolve_active_runtime_record` 原来对读失败、JSON 坏、目录不可解析、解释器不存在一律返回 `None`，
`select_active_record` 就跳到下一个候选目录——结果是"用户激活的运行时坏了"会被悄悄换成别的解释器。

现在区分三种情况：

- **文件不存在** → `Ok(None)`，正常走后续回退（首次安装、空壳 dev 目录都属于这种）；
- **文件存在但读不了/不是合法记录/解释器缺失** → `Err`，错误信息带指针路径与具体原因；
  `select_active_record` / `active_runtime_selection` 逐层向上传播，启动即失败而不是换解释器。

单测覆盖：坏 JSON 必须 `is_err` 且原文件不被改写、缺失文件仍返回 `None`、错误信息包含指针文件名。
**仍未对齐**：Python `worker_bootstrap._resolve_runtime_state_from` 依旧把异常吞成 `None`（读只读状态时
会显示"未激活"而不是报损坏），MCP 侧也没有独立诊断；下一步要统一这条语义。

## 1.24 P2 第五刀：Python 只读状态不再吞掉指针损坏

Rust 已经严格拒绝坏指针，但 Python `_resolve_runtime_state_from` 仍是 `except Exception: return None`，
`runtime_info` 会把"指针损坏"显示成"未激活"。

- 新增 `_load_runtime_state_from(file) -> (state, error)`：文件不存在返回 `(None, None)`；
  读不了 / JSON 坏 / 非对象 / 缺 `pythonPath` / 解释器缺失返回 `(None, 原因)`；
- `_resolve_runtime_state_from` 变成它的宽松视图，激活/写入流程行为不变；
- `runtime_info` 负载新增 `activeRuntimeError`（可用或不存在时为 `None`），诊断含指针路径与原因。

**边界**：这只改只读报告，不阻止激活/修复流程；前端暂未展示该字段。MCP 侧仍无独立诊断，
下一步可以把它接到了解状态的地方。

## 1.25 P2 第六刀：指针读取收敛到 shared

MCP 的 `_active_runtime_python` 是第三份独立实现，且有两个缺陷：相对路径按进程 CWD 解析、
损坏指针静默变成 `None`。

- 新增 `python/shared/runtime_pointer.py::load_active_runtime(file)`，规则与 Rust 一致：
  缺失 → `(None, None)`；读不了 / JSON 坏 / 非对象 / 缺 `pythonPath` / 解释器缺失 → `(None, 原因)`；
  相对 `pythonPath` 按**指针文件所在目录**解析，绝对路径保持原样。
- bootstrap 的 `_load_runtime_state_from` 改为调用它，再叠加 overlay 归一化（分层不变）；
- MCP 的 `_active_runtime_python` 改为返回 `(python, error)`，`Bridge` 保存 `runtime_error`，
  `status()` 新增 `runtimeError` 字段。

**仍未统一**：MCP 在指针损坏时仍然让 `OperationKernel` 用默认解释器（只报告、不拒绝）；
是否拒绝需要先决定"无激活运行时的 MCP 是否允许回退默认 python"。

## 1.26 P2 第七刀：坏指针下 MCP 拒绝运行时工作，查询不受影响

## 1.33 主题收尾：波形在切主题/换强调色后重绘

`EditorWaveform` 的 `--primary` 是画到 canvas 里的：切主题只改 CSS 变量，不会触发任何 prop 变化，
所以画布会一直保留旧颜色，直到别的属性让组件重绘。

现在组件挂载时用 MutationObserver 观察 `document.documentElement` 的 `style` / `class` / `data-theme`，
变化时重排一帧重绘；卸载时断开。新增 `tests/editorWaveformTheme.test.mjs`：

## 1.87 Windows worker 生命周期绑定

同步 worker 与后台 worker 都改为创建后立即
`ProcessJob::attach(&child)`；`WorkerStartResources` 持有 Job handle，直到子进程真正回收。

- App 崩溃/退出时 Windows 关闭 Job handle，`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 会杀掉
  worker 及其子树，不再留下继续写运行时/输出的孤儿；
- attach 失败会 kill+wait 子进程并清理 payload，再返回明确错误；
- 与下载进程、plugin audio host 共用同一个 `process_job` helper。

**范围**：这是 Windows 修复；Unix 仍没有等价的父进程死亡自动回收，需要后续用
process group + 监督/心跳方案补。macOS/Linux 的完整孤儿回收仍未验收。

验证：`pnpm test:rust` 516 通过 / 2 忽略。

## 1.88 Studio 父进程死亡：stdin 管道 + 进程组

Rust 为每个受监督 worker 建 stdin 管道并设置 `MEDIAFORGE_PARENT_PIPE=1`；
`worker.py` 启动 daemon watchdog 读取 stdin，父进程退出/崩溃时读到 EOF，Unix 上
`killpg(worker group, SIGTERM)` 终止 worker 及 FFmpeg/tool 子树，然后 `os._exit`。

- Unix 每个 worker 都是独立进程组 leader；
- Windows Job Object 仍是主回收路径，stdin watchdog 是第二道保险；
- MCP bridge 的 `OperationKernel` 也以 `stdin=PIPE` + `MEDIAFORGE_PARENT_PIPE=1` 启动 worker，
  POSIX 上 `start_new_session=True`；bridge 死亡时同样由 watchdog 回收；
- 直接 CLI 不经 bridge/Rust 启动的 worker 不设置该 env，避免终端 stdin 关闭误杀。

验证：Rust 516、Python 全量 **1715 通过 / 5 跳过**。

   - 如果需要真实窗口或弹窗自动化，必须在任务中明确授权测试范围和专用环境。
