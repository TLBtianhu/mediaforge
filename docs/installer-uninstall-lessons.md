# 安装与卸载：踩坑记录与项目守则

这份文档记录 MediaForge 在安装、升级、卸载、运行时安装和集成加载中遇到的问题，以及其它桌面项目可以直接借鉴的规则。

## 一句话原则

**安装器只负责部署程序；应用自己管理运行时、模型和用户数据。卸载默认保留用户资产，删除必须显式选择且只针对精确路径。**

## 1. 目录边界必须先定清楚

推荐单一安装根：

```text
<install-root>/
  app/             程序本体，升级时可以替换
  data/            配置、任务、日志等用户数据
  models/          模型权重
  runtime-envs/    独立运行时资产
  integrations/    外部宿主集成文件
```

规则：

- 安装器只部署 `app/`，不要在安装阶段顺手修复运行时。
- `data/`、`models/`、`runtime-envs/` 由应用按需创建和管理。
- 开发、便携、安装和桥接模式使用同一套路径解析器，不要各自推导目录。
- 开发数据必须隔离到开发数据根，不能使用真实用户或 dogfood profile。

参考：[worker_paths.py](../python/shared/worker_paths.py)。

## 2. 不要让安装器承担运行时修复

曾保留过 `RepairVenvConfig` / `RepairBundledRuntimeEnvs`，安装器会改写旧 `pyvenv.cfg` 和旧后端目录。这会把安装器变成第二套运行时管理器，带来路径冲突。

正确做法：

- 安装器不修改旧运行时配置。
- 运行时由资产 ID、SHA-256、大小和 `active-runtime.json` 管理。
- 新嵌入式运行时自包含，不依赖旧 venv 启动器或 `pyvenv.cfg`。
- 升级测试应验证旧 `pyvenv.cfg` 保持原样，而不是被安装器重写。

参考：[mediaforge.iss](../installer/mediaforge.iss)、[runtime_assets.rs](../src-tauri/src/runtime_assets.rs)。

## 3. 运行时资产必须支持断点续传和原子激活

运行时包可能达到数 GB，不能只用“下载成功/失败”的粗放逻辑。

必须具备：

- 内容寻址资产目录，例如 `runtime-envs/<assetId>`。
- 下载前校验 SHA-256 和大小。
- 下载中的 `.incoming-<assetId>` 保留，供下次续传。
- 下载失败时保留 aria2 stderr，给出可操作错误，而不是只显示 `ExitStatus(1)`。
- 解包和激活分离，只有验证成功后才切换 `active-runtime.json`。
- 回滚必须绑定同一个资产身份，不能跨资产复用旧计划。

## 4. 卸载窗口必须在真正卸载前出现

Inno Setup 的一个实际坑：`TNewForm` 不是可用的表单类型。卸载选项应使用 `TSetupForm` 和 `CreateCustomForm(...)`，并在 `InitializeUninstall()` 阶段显示独立的 `ShowModal()` 窗口。

不要依赖卸载进行中的表单状态，也不要把用户数据删除隐藏在默认流程里。

推荐行为：

- 默认只删除主程序、快捷方式和安装注册项。
- 只有用户明确勾选，才删除 `runtime-envs/`、`models/` 或 `data/`。
- 外部宿主集成由宿主自己的插件管理器处理，不由卸载器代管。
- 卸载完成后验证配置和模型仍在，而不是只验证程序目录消失。

参考：[mediaforge.iss](../installer/mediaforge.iss) 和 [smoke-upgrade.ps1](../scripts/smoke-upgrade.ps1)。

## 5. 删除必须精确，不能模糊匹配

禁止：

- 用通配符删除整个用户目录。
- 根据名称猜测哪些是“旧数据”。
- 删除共享目录中其它任务或后续派生产物。
- 因为用户卸载程序就默认清空模型、配置和历史。

推荐：

- 只删除明确登记的文件和目录。
- 对输出清理使用路径边界检查。
- 批量删除时保护输入文件、其它任务输出和共享目录。
- 对失败删除给出真实错误，不要静默报告成功。

## 6. 外部宿主集成不要写进安装器的私货逻辑

DSH 集成应通过 DSH 插件管理器加载，而不是安装器修改 DSH 配置或启动/重启 DSH。

需要区分：

- 应用自己的安装和卸载。
- 外部宿主的插件安装、启用、禁用和升级。
- MCP 桥接进程的启动和工具发现。

不要把三者混成一个安装步骤，也不要为了测试集成而修改真实宿主 profile。

## 7. Windows 启动器不要忽略批处理展开时机

在括号包围的批处理块中，`%MF_INSTALL_ROOT%` 可能过早展开，导致路径退化成 `\data`、`\models` 等错误值。

使用延迟展开：

```bat
setlocal EnableDelayedExpansion
set "MF_INSTALL_ROOT=..."
rem 在同一括号块中使用 !MF_INSTALL_ROOT!
```

启动器还应使用统一的 `worker_paths` 解析数据、模型和运行时路径，不要另写一套路径拼接。

## 8. 打包元数据也有大小限制

DSH 插件元数据曾因为内嵌 PNG 图标超过 256 KiB 而加载失败。解决办法是改用小型 SVG，而不是继续压缩一张大 PNG。

其它发行包也要注意：

- GitHub Release 单文件有大小限制，运行时包不要硬塞进应用安装包。
- 应用安装包、便携包、更新包和运行时资产分开托管。
- 更新包必须带签名，版本清单和签名要同步到所有镜像。

## 9. 测试必须使用隔离环境

安装和升级测试不能覆盖当前安装版，也不能使用真实用户目录。

推荐：

- 每次测试使用独立临时安装根和数据根。
- 保留失败现场用于诊断，但验证完成后清理临时目录。
- 测试覆盖升级、默认数据根、真实首装、SHA-256 负例和卸载保留数据。
- 应用正在运行时，测试探针要绕过单实例守卫，否则第二个进程会直接返回，造成“没有输出”的假象。
- CI 的 macOS 任务如果连续在 `macos-latest` 上被取消，应固定到已验证可用的 runner，例如 `macos-14`，并记录原因。

参考：[smoke-first-install.ps1](../scripts/smoke-first-install.ps1)。

## 10. 发布前检查清单

### 安装器

- [ ] 只替换 `app/`，不重写运行时配置。
- [ ] 不修改 DSH 配置，不重启 DSH。
- [ ] 不覆盖真实用户或 dogfood 数据。
- [ ] 不执行未经明确授权的旧目录迁移。

### 运行时

- [ ] 资产 ID、大小和 SHA-256 一致。
- [ ] 下载失败保留续传文件和真实错误。
- [ ] 激活指针只在验证成功后更新。
- [ ] 更新计划和回滚不跨资产。

### 卸载器

- [ ] 卸载前显示独立选择窗口。
- [ ] 默认保留配置、模型、运行时和历史。
- [ ] 删除只使用明确、精确的路径。
- [ ] 卸载后验证用户数据仍在。

### 验证

- [ ] 隔离升级测试通过。
- [ ] 真实首装与坏哈希负例通过。
- [ ] 生产构建和签名完成。
- [ ] 综合 CI 通过。
- [ ] GitHub 与镜像的清单、产物和签名回读一致。

## 最容易复发的问题

> 把“安装程序能做什么”误当成“应用应该替用户做什么”。

安装器不应该替用户修复运行时、迁移数据、修改外部宿主或删除历史。它只负责部署程序；其余生命周期必须由应用内部明确、可验证地管理。

## 安装器排除规则必须锚定包根目录（2026-11-08）

0.0.34 的真实独立身份验收发现，未锚定的 models\*、data\* 会匹配深层同名目录，
误排除 python-runtime/Lib/site-packages/pip/_internal/models/candidate.py 等依赖代码。
仅验证 EXE 或 health 不足以确认 bootstrap 完整，必须逐文件核对完整 stage 的安装结果。

Inno Excludes 的前置反斜杠将匹配范围限定在输入树根部，因此用户资产排除使用
\models\*、\data\*、\python-runtime\runtime-envs\*；不按目录名全树误杀依赖源码。
依据：[Inno Setup 官方 Files/Excludes 文档](https://jrsoftware.org/ishelp/topic_filessection.htm)。
这属于打包完整性修复，不是旧格式兼容或迁移。
